# SDUI config — the home-config payload

The flat string map every Stationly client reads its words, thresholds and rules
from, and the rules for changing it safely.

Client companion: `StationlyUI/docs/SDUI.md`.
Live key inventory: `StationlyUI/docs/CONFIG_KEYS.md` (generated).

Last updated 2026-08-31.

---

## 1. The one rule

> ### Adding a key is safe. Removing one is not.

**Android is the live production client, frozen at versionCode 2, with no
rollback.** It reads this payload. A key you remove that a shipped Android build
still reads renders a **blank string in production**, and there is no release to
fix it with — the app is frozen.

An unread key costs a few bytes. Retire a key by documenting it as unread in the
inventory, never by deleting it.

This rule is not theoretical. An audit once classified 37 keys as "dead payload"
because no *iOS* client read them. **Thirty were live reads in production
Android.**

### The corollary

You cannot verify from this repo what the shipped Android binary reads. The
`android/` tree in `StationlyUI` is ahead of the store build by an unknown number
of commits. Treat any "no client reads this" finding as a floor, never as
permission to delete.

## 2. The endpoint

```
GET /api/v1/sdui/app/home-config
Header: X-Stationly-Key: <client key>

→ { "id": "home_config", "strings": { "<key>": "<value>", ... } }
```

Everything is a **string**. Numbers, booleans and lists are string-encoded and
parsed client-side:

| Shape | Example key | Example value |
|---|---|---|
| plain copy | `empty.title` | `Your board is empty` |
| number | `board.tick.departedGraceMs` | `30000` |
| boolean | `home.promo.support_money.show` | `false` |
| comma list | `board.status.severityOrder` | `Closed,Suspended,…` |
| JSON document | `support_money.card.json` | `{"type":"support_money_card",…}` |
| template | `explore.status.count.delayed` | `{n} delayed` |

Template placeholders (`{n}`, `{t}`, `{s}`, `{age}`, `{total}`) are substituted
by the client. **Keep them** when editing a value.

Sibling endpoints, separate payloads: `/theme-tokens`, `/refresh-policy`,
`/home-announcement`, and the per-screen layouts
(`/login`, `/register`, `/forgot-password`, `/about`, `/selection`).

## 3. Where the keys come from

`SduiService.getHomeConfig()` in `src/services/sduiService.ts` is the assembly
point. Most keys are literals in its map; three services spread their own blocks
in:

| Source | Contributes | Gated by |
|---|---|---|
| `sduiService.ts` literals | most families | — |
| `lineSeverityService.homeConfigKeys()` | severity order, red set, 21 display names | — |
| `supportMoneyConfigService.homeConfigKeys()` | `support_money.*`, `home.promo.support_money.*`, the card JSON | `SUPPORT_MONEY_ENABLED` |

**A source-level grep of this file will under-report the payload**, because the
spread-in keys are generated in loops and never appear as literals. A scan once
reported 177 keys where the real payload had 239. To enumerate the payload,
**run it**:

```bash
npx ts-node -e "const s=require('./src/services/sduiService');\
console.log(Object.keys((s.SduiService||s.default).getHomeConfig().strings).length)"
```

**Two keys are read but deliberately NOT served:**

- `board.good_service_sub` — an optional override. The board falls through it to
  `explore.good_service_sub` so one phrase covers the state everywhere. Serving
  it freezes the board's copy apart from the Network section's and breaks that
  link. Set it only to make the two differ on purpose.
- `explore.status.dialog.title.disrupted` — Android composes it from a count with
  singular/plural agreement (`1 line is` / `3 lines are`), which a flat string
  cannot express. It stays client-side until the key can carry a plural form.

## 5. `lineSeverityService.ts`

One table, three wire forms, so the ordering, the tone and the wording of the TfL
severity vocabulary can never disagree.

```ts
{ tfl: 'Bus Service', display: 'Replacement buses', tone: 'amber' }
```

| Wire form | Key(s) | Consumer |
|---|---|---|
| ordering | `board.status.severityOrder` | which disruption a multi-line board leads with |
| tone | `board.status.redSeverities` | which severities make the indicator dot red |
| display | `explore.status.severity.<lowercased, spaces→underscores>` | what the sheet shows instead of TfL's own word |

`tone: 'green'` entries (`Good Service`, `No Issues`) are excluded from the
ordering — a board shows "Good service" only when every line is good, in which
case one line says it for the whole board. They are in the table for their
display name.

**Red means "you cannot travel on this line right now"** — closures and
suspensions. Delays and reduced service are amber: a train is still coming, and
someone who sees red should change their plan rather than expect to wait.

**Adding a severity is one row.** Order, tone and wording move together.

The display keys are the notable win: both clients have read
`explore.status.severity.*` since they were written and nothing ever served them.
Emitting them lights the family up on **production Android with no Android
release**, because the reader was always there.

## 6. The client contract

Assume this on every value you serve.

| Guarantee | Meaning |
|---|---|
| **A missing key is fine** | every client ships a compiled default and renders correctly having never reached this endpoint |
| **A blank value is treated as ABSENT** | a half-finished edit falls back to the default rather than shipping a screen with no words |
| **Numbers are clamped** | out of range moves to the bound, not the default — `5000` against a max of `120` becomes `120` |
| **Lists fall back** | `","` cannot erase an ordering; an unusable list keeps the compiled one |
| **Config lands on the next fetch** | values are cached on device and applied on the next launch or sync, not instantly |

Client-side clamps (`StationlyUI/core/config/BoardPolicy.kt`):

| Key | Clamp | Why the bound exists |
|---|---|---|
| `board.tick.departedGraceMs` | 0 … 120000 | — |
| `board.tick.retentionMinAgeMs` | 15000 … 600000 | — |
| `board.tick.departedLabel` | ≤ 6 chars | it sizes the ETA column, which is what the destination truncates against |
| `board.tick.rowReserve` | 5 … 20 | a reserve below the deepest board a user can set renders that board short |
| `board.stale.freshMs` | 15000 … 600000 | — |
| `board.stale.staleMs` | ≥ freshMs | red must never come before grey |
| `auth.password.min_length` | 6 … 64 | Firebase enforces 6; a lower value has the form accept what the network rejects |
| `auth.verify.resend_cooldown_sec` | 10 … 600 | it gates a button: 0 is an unlimited send loop, an hour is a dead control |

**Two coupled keys.** `board.stale.freshMs` and `board.tick.retentionMinAgeMs`
are the same number by default on purpose — the footer going grey and the rows
going "Gone" are one statement about one payload. Serve `freshMs` alone and the
client moves retention with it. Serve both to mean them differently.

## 7. Changing a value safely

1. **Edit the value. Never remove the key.** (§1)
2. **Keep template placeholders** — `{n}`, `{t}`, `{s}`, `{age}`, `{total}`.
3. **Check who reads it** in `StationlyUI/docs/CONFIG_KEYS.md`. A key marked
   `android` renders on the production app the moment you deploy.
4. **Respect the clamps** in §6, or the client silently pins your value to a
   bound.
5. `npx tsc --noEmit && npm test`
6. `bash .scripts/staging_deploy.sh`
7. **Verify against the live endpoint**, not the source:

```bash
KEY=$(sed -n '66p' ../StationlyUI/iosApp/Config/Staging.xcconfig | cut -d= -f2- | tr -d ' ')
curl -s https://staging-api.stationly.co.uk/api/v1/sdui/app/home-config \
  -H "X-Stationly-Key: $KEY" | python3 -m json.tool | head -40
```

### Before any structural edit

Run the removal guard from the client repo:

```bash
python3 ../StationlyUI/scripts/sdui_keys.py --check
```

It builds this payload, compares it against the committed inventory, and fails on
any key that has left — naming the client that reads it.

**It has caught a real incident.** A regex replacement intended to span one key
spanned thirty-seven, deleting 36 keys. `tsc` was perfectly happy. They were
recovered from a deployed staging payload because the file was uncommitted at the
time — a deployed server is not a backup.

## 8. Environment gates

| Variable | Effect |
|---|---|
| `SUPPORT_MONEY_ENABLED` | master switch for the whole `support_money.*` family and the card JSON. `false` unless explicitly `true`. |
| `SUPPORT_MONEY_PROMO_ENABLED` | `false` suppresses `home.promo.support_money.show` independently of the master switch, so the permanent profile card can stay while the interruption is off. |
| `SUPPORT_MONEY_MIN_BOARDS` | default 2 |
| `SUPPORT_MONEY_MIN_DAYS` | default 3 |

Staging and production therefore serve slightly different values for four
support keys. That is expected and is not a payload regression.

## 9. Verification checklist

| Check | Command |
|---|---|
| types | `npx tsc --noEmit -p tsconfig.json` |
| tests | `npm test` (180/180 at time of writing) |
| payload size | run `getHomeConfig()` (§3) |
| no key removed | `python3 ../StationlyUI/scripts/sdui_keys.py --check` |
| live payload | curl the endpoint (§7) |

To diff HEAD's payload against the working tree, build HEAD in an **isolated git
worktree** — a `git stash` cycle races with the probe and produces a bad capture.
Sort both key lists under **`LC_ALL=C`**: the default locale collates `.` and `_`
differently from `comm`'s byte comparison, which has produced a false "two keys
removed" report.
